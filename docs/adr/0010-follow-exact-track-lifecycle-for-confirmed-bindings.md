# Follow Exact Track Lifecycle for Confirmed Bindings

A confirmed Durable Track Identity Binding is active only while it remains confirmed, has no explicit termination time, and its expiry is later than the current time. Creation and throttled heartbeat derive expiry from the latest observation of the exact Store, camera, Runtime instance, and Track token plus the configured track-lost interval. Ordinary Track loss stops heartbeat and removes the Cache projection but does not write an explicit termination time; conflict and supersede remain explicit lifecycle termination facts. A new Runtime never renews or restores a prior Runtime's Binding.

Finalization and lifecycle heartbeat use one narrow, read-only query over the current StoreRuntime Track snapshot buffer to obtain the latest immutable snapshot for the exact Store, camera, Runtime instance, and full Track token. The buffer lock is released before any SQLite transaction begins; callers decide whether the returned snapshot is still active and never fall back to another Runtime or to historical Evaluation evidence.

The new-mode Store Runtime owns a throttled heartbeat loop outside the video-frame path. Each tick closes its candidate read session before consulting the snapshot buffer, then uses one fenced `BEGIN IMMEDIATE` batch to revalidate and only extend still-active Bindings when the captured Track activity remains current at transaction time. A second Lease fence precedes commit; only afterward may the shared Cache be refreshed from the final committed Binding values. Expired or terminated Bindings are never revived, missing or lost Tracks are invalidated from Cache, and Runtime stop or Lease loss joins the loop before clearing that Runtime's Cache scope.
